# DocTransAI 新支线技术方案与代码结构

日期：2026-09-05。开发分支：`codex/document-tools-refactor`。代码基线：`40164d5`。

本文描述目标方案及实施顺序，不代表相关模块已经实现。当前新支线继承旧系统代码，并有一个独立的文档工具实验脚本；本次只新增设计文档。

## 1. 产品目标与范围

用户提供 DataProxy 交付产物、目标模板和本次转换要求。系统理解材料与模板，在模板副本中组织和填写内容，产出可编辑文档、页面预览和简明的待确认事项。

统一支持三类工作：准确转填已有事实；依据材料进行摘要和内容组织；按条目展开表格行或图文块。正确留空也是有效结果，不能以填充率最大化为目标。

目标输入为 DataProxy 对 DOC/DOCX、XLSX、PDF 等源文件的解析产物；目标模板及可编辑输出为 DOCX、XLSX。PDF作为源材料和预览格式，暂不作为编辑目标。已有 DOC 模板须在进入编辑流程前明确转换为 DOCX并验证，不能默认为原生支持。

模板版式原则上保留，但允许按内容展开行、段落和图文组，页数可合理增加。固定文字、公式、页眉页脚和人工签署区域不能被无意改写。

最先提供一个可运行的 Python 接口和 CLI，后续界面复用同一个转换入口。当前不建设Web平台、账号系统、任务队列、数据库或插件框架。

## 2. 实验依据及结论边界

2026-09-05实验使用 `kimi-k3`，经过当前配置的 DashScope 接口真实调用。

| 实验 | 已观察到的能力 | 对方案的约束 |
| --- | --- | --- |
| 台账单行到整改记录单 | 生成2页、3张图；依据K6/T6/Y6锚点排除相邻行图片，分别填写检查、整改、复查内容 | 对象范围必须明确；保留原生表格锚点，不能只相信宽泛的图片关联列表 |
| 两条隐患到通知单 | 模型自行选择重复图文块，最终2页、2组图文 | 首轮误用源通报文号和日期，需要外部复核；图与说明应作为一个编辑整体 |
| 长篇科技成果到信息表 | 流式及小批次编辑后生成4页，完成事实转填和长文本整理 | 非流式请求曾发生180秒、300秒等待超时；不可只扩大请求或等待上限；需明确长度口径及申报主体 |

其他直接发现：原生对象的章节标题可能包含重要事实；源图片相对路径需结合 source_manifest 中的文档哈希解析；读取未定义页眉不能创建页眉；写入不能重序列化并改动不相关的包部件；预览不能复用旧文档版本的缓存。

三个实验仅验证了DOCX输出，且发生过工具修复、续跑和一次外部语义纠正。没有在同模型条件下与旧主链做完整对照，不能声称性能、成本、准确率已整体胜出。

## 3. 核心架构

主流程为：明确任务范围 → 读取原生材料及模板 → 模型调用文档工具编辑副本 → 渲染与检查 → 有限修正 → 交付文件及问题清单。

实现上只有一个模型执行循环。模型根据当前材料和工具返回决定下一步，代码负责执行可靠、有限的文档操作。无需多智能体调度框架。

原方案以预先发现的槽位为权威任务清单；新方案以整份目标文档为工作单位。结构读取提供精确地址，视觉提供版面理解，模型确定哪些位置要填写、保留、清空或展开。结构地址不预设业务含义，也不限制模型只能处理某份预选槽位清单。

保留稳定的文档编辑协议；不再建立 SourceModel、候选集合、槽位决策、RenderPlan 等层层转换。一次工具调用可以携带一批明确编辑操作，代码直接执行，不再把这些操作转换为另一套渲染计划。

## 4. 任务范围先于填写

转换任务至少包含：bundle路径、选定源文档、模板、输出位置、自然语言要求。可选指定记录/章节范围、内容长度限制和输出组织方式。

输出组织方式包括：汇总成一份文档；只处理指定对象；每个对象生成一份文档。不要在逐字段填写过程中隐式决定对象范围。

没有指定时，先结合材料及模板判断。如果“多条问题汇总”和“一条一单”均合理，形成一个明确待确认问题，不能自行选一条材料或混合不相关记录。一对多输出先确定对象与来源范围，再复用单文档转换函数；不引入通用业务实体平台。

用户确认的对象范围在整个任务及续跑中保持有效。工作表行号、图像单元格锚点等原生信息可用于核实范围，但相邻文本或关联ID不自动代表属于同一对象。

## 5. DataProxy 数据接入

复用现有bundle读取及契约检查能力。构建一份轻量材料视图，引用原生 evidence、section、block、table、range和asset对象；不重新创造统一业务字段模型。

初始输入提供文档说明、对象范围、可读正文/表格及图片索引。短材料可直接给全量；长材料先给目录和概览，支持按原生引用、章节或关键词读取原文及邻接上下文。第一版使用现有结构和普通文本搜索，无需向量数据库。

同一表格不要同时展开成表、行、格和重复正文再一起发给模型。去重只处理重复表示，不删除独有事实。完整对象留在本地可查询，工具返回明确披露分页、截断和仍可读取的范围。

引用应解析到原始对象及其上下文，包括 text、locator.section_title、表头、单位、范围及图像关联。校验不能只搜索正文字符串，也不能通过全文命中替换错误引用。

图片路径结合bundle根目录、source_manifest中的文档哈希及source_ref解析。多个候选不能取第一个猜测；不存在或存在歧义时返回明确错误。源文件、bundle和模板均以输入资料处理，生成物写入独立任务目录。

## 6. 视觉输入的三种角色

| 对象 | 策略 | 用途 |
| --- | --- | --- |
| 源文档页面 | 按需读取；明显依赖版面的材料可在初始阶段提供相关页 | 核实图文关系、表格归属、复杂版面和结构化歧义 |
| 源图片资产 | 按需查看缩略图或原图 | 选择真正要插入的图片，结合原生锚点和上下文判断所属对象 |
| 目标模板 | 默认提供页面预览和准确结构；较大模板分段阅读并记录覆盖范围 | 理解隐式空白、固定文字、重复区域和内容容量 |
| 最终输出 | 必须检查最新版本的全部输出页，可分批检查 | 发现裁切、错位、图文分离、异常分页及可见遗漏 |

新增 view_source_page 工具。优先读取DataProxy已交付且可识别的页面图；没有时，从任务指定的原文件生成辅助预览。不重复建设OCR或文档解析管线，也不把源文件重新抽取一遍绕开DataProxy。

必须区分DataProxy的page_anchor与本地渲染页码，特别是DOCX重新分页、Excel打印页与工作表行之间的关系。工具返回文档、实际页面及对应关系是否可靠，不能假定两个页码天然相同。原文件不可用且无页面图时，明确记录视觉能力缺口。

页面可帮助确认已有事实和关系。若页面显现关键文字但原生交付缺失，记录证据缺口或待确认项；不静默把它当作已有结构化事实。截图也不自动等同于可插图资产；如以后支持从页面裁图，应保留父页面、裁切区域和来源关系，不能混入原生图片ID。

缓存按输入内容哈希、渲染配置和渲染器版本区分；输出预览绑定文档版本。模型只能基于实际收到的页面报告检查结果，不能把“文件已渲染”当作“页面已审阅”。

## 7. 文档工具及编辑能力

模型端保留少量工具入口，不按业务字段建立工具：

| 工具 | 职责 |
| --- | --- |
| read_source | 按引用、章节、范围或关键词读取原生材料和上下文 |
| view_source_page | 查看指定源文档页面及必要局部区域 |
| view_source_asset | 查看独立图片及其原生锚点、关联信息 |
| inspect_document | 返回当前模板/文档结构、精确地址、格式限制及支持的编辑能力；支持局部读取 |
| edit_document | 在指定地址应用一批文字、图片、表格行或图文组编辑 |
| preview_document | 渲染指定文档版本，返回页面和检查所需的结构摘要 |
| finish | 提交完成声明、缺失项及待确认事项；程序继续检查交付条件 |

DOCX目标能力：段落与单元格文字替换、保留run格式的局部替换、有意义的分段/列表、图片插入、连续段落或表格行重复，以及有限的对齐和分页控制。图文组内可一段描述对应多张图，重复时保留组内关系。复杂文本框、浮动对象或嵌套结构在支持前显式报告能力缺口。

XLSX目标能力：单元格/区域填写、按表头展开行、合并单元格感知、图片锚定与尺寸约束、必要行高调整。保护原有公式、格式和打印设置；复制行涉及公式引用、合并区域或图像锚点时必须有对应格式测试，不能直接套用DOCX规则。

两种格式共享inspect/apply接口和任务循环，具体操作按能力声明分派到两个后端。无需将所有格式的地址塞进一个充满可空字段的通用结构。

节点ID由程序生成，绑定当前文档对象和版本；显示段落位置、表格坐标、附近文字以便理解。编辑后返回仍有效或新增的地址；过期地址明确失败并要求重新读取。重复标签不能按“首个/末个匹配”自动定位。

操作前检查地址、范围、必要参数、引用和图片可用性；整批成功后再保存，失败不能留下半批修改。记录操作ID及编辑前后文件哈希，续跑按已成功操作恢复，不重复插图或重复复制行。

引用检查只检查可解析性与任务范围，不宣称证明语义。删除无依据的占位符或保留固定标签，不需要虚构来源。模型使用受支持的编辑工具，不通过任意Python、Shell或自由生成OOXML完成任务。

## 8. 模型执行与配置

默认模型为kimi-k3，模型名、接口和密钥集中于配置入口。复用现有LLM客户端并补充工具调用与流式处理，正式实现删除实验脚本中重复的HTTP客户端及硬编码路径。

优先使用DocTransAI专用配置；可显式配置DataProxy环境文件作为兼容来源，识别本次实际使用的DATAPROXY_GENERATION配置。只读取所需键，缺失时给出配置错误，不硬编码用户名、目录或密钥。

默认采用流式工具响应；只有参数完整、解析成功、通过检查后才执行操作。输出截断时返回可恢复错误，不能执行半段JSON。

长文本按文档区域分批编辑，起步以每批不超过4个复杂单元格作为可调运行策略，不作为永久业务规则。简单短字段可批量提交。图片按需发送，历史消息不重复塞入整份源材料和所有页面；可用锚点和操作摘要减少历史长度，但不能压缩掉尚未核实的事实。

执行步数、输出预算、网络等待和修正轮数都可配置并有上限。预备采用12个执行步骤、最多2轮结果修正作为初始试验值，后续按同口径样本调整。达到上限返回当前文件及未完成原因，不伪装成成功，不无限自修复。

传输重试不能重复执行已有编辑。保存必要模型消息、工具结果和检查覆盖即可恢复；日志不包含密钥或图片base64正文。记录完整任务耗时、每次调用耗时及usage，包含重试阶段；超时缺失usage标为未知。

## 9. 提示词管理

主提示词文件为 prompts/document_editing_policy.md，职责仅包括文档理解、事实使用、对象一致性、图文关系、未知项处理、工具使用与完成要求。

工具参数和能力说明在tools.py及格式后端中维护，避免在提示词重复一份schema。任务要求由每次调用输入提供，包含对象范围、目标文体、长度口径和明确允许的归纳方式。实验复核反馈留在对应run中，不自动沉淀为通用规则。

复核使用一份较短的 prompts/document_review_policy.md，明确要求从最终文档与源证据重新判断，避免沿用生成者的理由。它是检查视角，不承担工具定义或业务流程编排。

不为每个样本、模板或业务角色创建一份提示词。确有模板特有要求时作为模板说明随任务传入，先不建设模板注册平台。每次运行记录提示词内容哈希，便于比较行为变化。

## 10. 结果检查与交付

检查分为三个互补部分，但无需三个调度服务：

1. 确定性检查：文件可打开、操作实际落位、图片可解析、固定内容及公式未被意外改写、没有失败操作遗留、长度符合已声明口径、最终预览对应最新文件。
2. 模型复核：使用新的上下文查看最终输出页、实际写入内容、相关完整原生证据和任务范围。可按需读取来源，仅开放只读工具。重点检查错填、漏填、对象混杂、日期/角色错用和图文关系；不要预先把生成者的“正确理由”当作结论。
3. 必要的用户确认：材料歧义、申报主体不明确、源数据冲突或明确的人工签署事项，形成简短清单。普通转换不增加一律需要人工批准的步骤。

独立上下文不等于独立真值；同一模型可能重复同样的错误，不能承诺消除幻觉。程序做确定性保证，语义结论仍带明确的复核范围。

结果至少区分execution_status（completed/failed）与review_status（passed/needs_review/not_run）。文件生成成功不自动代表内容检查通过；支持性原文缺失的正确留空也不自动代表执行失败。

默认交付可编辑文件、最新预览和简明问题清单。问题区分源缺、歧义/冲突、人工项、工具不支持及实际生成错误；避免恢复多份互相重复的审计报表。

## 11. 最终目标代码结构

以下是重构完成后的目标结构，不是要求立即创建所有空目录。保留少量稳定职责，功能做到哪里再建立对应模块。Python包常规__init__.py在树中省略。

├── pyproject.toml
├── uv.lock

│   └── document-tools-architecture.md
├── src/doctransai/

│   ├── config.py                 # 模型、运行预算、渲染器与资料路径

职责依赖：cli调用conversion；conversion组织agent和review；agent经tools调用data_layer及documents；documents不调用LLM、不判断业务；data_layer不判断目标如何填写。review复用相同的材料读取与预览能力。

最终对外入口建议为convert(TaskSpec) -> ConversionResult。CLI只是该函数的包装。一对多转换按已确认范围调用同一函数，避免另建一条平行主链。
