# K3 直接使用办公工具与 DocTransAI 的案例对照

## 结论和证据范围

本案例说明预先准备源材料和封装文档工具可以减少工具探索与返工，但没有证明 DocTransAI 已达到可接受延迟。用户侧“原生”运行实际是 K3 max 加腾讯本地办公 MCP、shell 和技能，不是裸模型 API，也不是无工具的一次推理。没有其逐请求日志，不能把 32 分钟归为纯模型思考，更不能把约 55 次工具调用与本项目 4 次模型请求作同口径比值。

已读取完整复盘：`/Users/paul/Documents/AI协作/DocTransAI整改通知单转换-流程复盘.md`（约 8 KB）。32分19秒来自用户和复盘记录；八阶段时长是事后估计，表格加总约34分钟，不是严格计时分解，不应据此绘制精确占比图。未取得原生每请求 token、服务商实际配置和完整工具轨迹。

本轮没有重新运行模型或测试矩阵，只做文件结构审查、当前 DOCX 渲染与两页目检、既有项目日志复核。当前用户给定的模板路径已存放原生结果，Git 标记为修改；保持该文件原样，不恢复覆盖。原始模板仅从 Git 取到审阅目录作对照，后续测试不能误将已填结果视为空白模板。

## 结果文档审核

但不能认定格式完全保真：

- 原模板首个合并单元格有6个段落，结果变成1段。责任单位、正文与落款失去原有分段关系；日期紧接正文结尾，单位名称被空格及段落格式拉成分散排布。2页比本项目3页少，不代表质量更高。
- 两张图注的直接字号分别16pt和10.5pt，实际页面第二条显著更小，样式不统一。
- 检查人员填写的是源文的参与部门与群体描述，不是个人姓名；这是有来源的群体表述，但模板是否接受这一口径仍需确认，不能说比留空必然更完整或正确。
- 落款日期沿用原通报/检查日期，源文没有明确授权新通知单的签发日期。整改监督人/负责人也存在角色迁移。与本项目相同，业务事实边界仍未自动解决。
- 用户给出的输出路径与原模板路径相同，当前文件确实已变更。若产品要求保留原模板，应始终另存副本；本轮不猜测该原生会话是否曾获得原位修改授权。

## 同口径比较

| 指标 | K3加办公MCP直接处理 | DocTransAI最新图文组版 |
|---|---|---|
| 任务总耗时 | 用户/复盘记录1939秒 | 转换日志638.830秒；上游解析与取包另约8.03秒 |
| 输入 | 原始DOC和模板 | DataProxy正式包、原文页面和模板 |
| 模型档位 | 用户称max，未取得请求日志 | kimi-k3/max客户端配置，DashScope |
| 模型请求数 | 未知 | 4 |
| 工具调用 | 自述约55次 | 4次模型工具调用：inspect、edit失败、edit成功、finish；另有程序自动渲染 |
| 成品 | 2页、2图、独立图注 | 3页、2图、独立图注 |
| 格式 | 首单元格分段塌缩、图注字号不一致 | 分段保留较好，仍较疏松 |
| 语义 | 日期/人员角色推定 | 同类推定，模型报告needs_review |

把约8.03秒上游耗时计入，本项目本案例约646.86秒，较1939秒少约66.6%，约为其三分之一；这是不同工具栈的单案例描述，不是受控性能结论，也不是所有文档的稳定加速承诺。开发投入不计入单次运行延迟；此前实现的大量解析、编辑工作解释了为什么能省去重复探索，不能成为十分钟延迟可接受的理由。

## 复盘中哪些问题已经解决，哪些仍在

原生复盘的DOC长文截断、取图失败、查工具schema、运行时发现不支持尺寸、坐标漂移、列表编号继承、空白尾页和渲染服务繁忙，属于模型加具体工具通道的摩擦，不全是K3模型能力。DataProxy已承担源文解析与资产交付；本项目工具schema随请求给出；repeat_paragraphs、set_list、版本校验、原子写入和本地预览已有对应能力。不要再把这些内容全部追加成新的提示词，更不要引入原生通道的textutil/soffice绕行规则。

本项目四次请求的实测耗时：

| 请求 | 结束动作 | 耗时 | reasoning tokens |
|---|---|---:|---:|
| 1 | inspect_document | 130.178秒 | 3934 |
| 2 | edit_document（偏移错误，被拒） | 279.998秒 | 5429 |
| 3 | edit_document（自行恢复成功） | 69.518秒 | 633 |
| 4 | finish | 148.964秒 | 3816 |

模型请求累计628.658秒，占转换98.4%；其余约10.17秒。请求时间包含服务等待、输入处理、传输和生成，不等于纯思考时间。首次索取模板细节之前已消耗130秒，生成失败编辑又消耗280秒，最后确认花149秒；不是单靠少一次本地渲染能解决。错误恢复直接增加约69.5秒，消除它并不自动消除先前280秒，不能把全部失败请求耗时都算作可节省量。

四请求累计输入163452 token，其中图片84564 token；图片40次携带（11、11、11、7），并非40张独立图片。推理token共13812。后续上下文有缓存命中，不能把累计输入当作全量未缓存成本。

## 建议：短决策规则与确定性编辑分工

### 先试提示词整理，不继续堆规则

将已有重复原则整理为可执行的决策次序，明确默认行为与例外；业务内容仍由源文和模板决定。建议方向如下，尚未实现或验证提速：

1. 唯一占位文字使用 replace_text；不同条目用已有重复组；需要字符范围时才索取该段细节。源与模板已提供的材料不再无目的重读。
2. 图片/正文冲突时对照已提供页面；caption不是事实真值。无法消除的角色或日期歧义留空并记录，不循环猜测，也不先推断填入再仅在报告免责声明。
3. 非必要布局不改动。不得为了减少页数压缩原有段落、合并固定布局或反复追求“更漂亮”；只修复明确的裁切、丢失、错配和不可读。
4. 当前版输出检查一次覆盖主要内容、逐图说明、固定布局和明确缺失。无具体缺陷则结束；有问题定位后局部修正，不重新规划整份文档。
5. 工具错误已经返回真实范围/原文时，利用这些事实精确更正；不要再次猜偏移。预算不允许完成时如实失败，不能跳过检查报成功。

这些规则按证据状态和文档结构选择，不按单位、人员、字段业务含义或样本名分支。不把“所有图片必须独立说明”写死，同一条目确实共用说明时仍可多图。

### 如果偏移依然是成本中心，再作最小工具改进

保留现有 replace_text，不重建槽位分析器。对只有重复空白、混合run/下划线、隐藏字符而无法唯一文字匹配的位置，可考虑由程序提供版本绑定的局部span句柄与左右文/格式，模型选择句柄并填值，程序计算字符位置和保留run。它只解决“改哪里和怎么保格式”，不决定“应该填谁、填什么日期”。仍须校验版本、预期文本、保护边界和原子写入；不允许错位时模糊匹配自动猜位置。此为候选设计，尚未实施。

### 再调整输入和验收口径

- 首轮可针对需要范围编辑的段落预供必要run细节，避免模型先花130秒才决定inspect；不能把全文件所有格式属性无差别展开。
- 短源的页面与独立图片存在视觉重复，后续可只改变一个输入策略做对照，不为了省图丢失来源上下文。
- 模型最终回复无需复述全量填写字段，可用简短完成说明与未决问题；不要求额外输出长推理链，也不声称“让模型少想”就必然提速。
- 档位优化在确认实际服务商支持后另做；目前仅客户端max/high记录不够证明服务端行为，不能据此立刻切换默认。

## 验证顺序（未执行新测试）

先冻结现有版本和原始模板，离线整理短决策规则及操作契约。获准继续测试后，选不同结构的少量代表任务（明确占位符、混合格式空白、重复图文组），保持同一输入/模型配置，仅比较一个变量。记录总时间、请求数、失败恢复、输出质量；必要时交错复跑确认波动，不立即跑大矩阵。首个可操作目标是正常路径不再为格式定位或参数错误额外往返，同时实测总时长下降且保真不退步；不能现在承诺固定2轮或某个分钟数。
